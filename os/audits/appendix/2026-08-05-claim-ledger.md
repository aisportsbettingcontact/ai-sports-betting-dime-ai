CLUSTER: The Python ML engine
====================================================================================================

[PARTIALLY_VERIFIED] A "Python ML engine" exists — where (ml/, scripts/, server/)? How is it invoked from the Node app?
  -> A Python engine really exists and really is spawned from Node — but it lives in server/, not ml/, and it is NOT machine learning. It is hand-written statistical simulation (Monte Carlo over negative-binomial / Poisson distributions) with hard-coded, offline-fitted constants. Invocation is child-process spawn with JSON over stdin/stdout: mlbModelRunner.ts spawns `python3 -c` with a generated driver that does `from MLBAIModel import project_game`; nhlModelEngine.ts spawns `/usr/bin/python3.11 nhl_model_engine.py`; strikeoutModelRunner.ts execFiles `python3 StrikeoutModel.py`. Separately, ml/ contains exactly one thing — ml/dime-1.0/, the LLM (QLoRA/Llama-3.1-8B) post-training lane, which CLAUDE.md itself marks DORMANT and which is unrelated to sports projections. Calling this an "ML engine" is a misnomer; "Python simulation engine" is accurate.

[VERIFIED] Monte Carlo simulation, ~400K iterations for MLB — the actual iteration-count constant is 400,000
  -> Exactly 400,000, defined once at server/MLBAIModel.py:68 and passed through unchanged at :2821. The engine clamps any caller-supplied value to [250_000, 500_000]. The sampling is real: NBGammaMixtureDistribution.sample() draws with numpy's default_rng (server/MLBAIModel.py:884 `self.rng = np.random.default_rng(seed)`), plus a separate simulate_extra_innings() path (:819).

[PARTIALLY_VERIFIED] Dixon-Coles Poisson for soccer
  -> A genuine Dixon-Coles low-score-corrected bivariate Poisson exists and is shipped — but it is JavaScript (server/wc2026/v27_jul18_engine.mjs, a .mjs spawned by wc2026Heartbeat.ts), NOT Python, so it is not part of the Python engine at all. It is also scoped strictly to the 2026 World Cup (file header names the 3rd-place match M103 and Final M104, dated 2026-07-18/19 — both already played), not to soccer generally. The file header line 9 advertises a "500X Monte Carlo backtest", which is false: there is no RNG in the file; buildJointMatrix is a closed-form 10x10 joint probability matrix and "500X" is a label for 25 parameter variations x matches (:605). server/dime/wc2026Context.ts:214 and dime-wc2026.route.ts:276 correctly instruct the chat layer to say analytical, not Monte Carlo.

[VERIFIED] MLB has model code
  -> Full simulation model (400K-sim Monte Carlo, NB-Gamma mixture, extra innings, market derivation, edge detection) plus a separate 100K-sim strikeout-props model and a recalibration backtest. This is by far the most complete sport.

[VERIFIED] NHL has model code
  -> Real correlated-negative-binomial Monte Carlo model at 200,000 sims (not 400K — that is MLB only), with goalie GSAX multiplier, fatigue and home-ice factors. Scheduled and manually triggerable.

[REFUTED] NBA has model code
  -> NBA is data ingestion only: Action Network / VSiN odds and splits, ESPN schedule fallback, and historical schedule+result grading into nba_schedule_history. There is no projection, simulation, or model code for NBA.

[REFUTED] NCAAM has model code
  -> The NCAAM model existed historically (KenPom-driven model_v9_engine.py + ncaamModelEngine.ts + ncaamModelSync.ts) and was deleted in commits e0139d4c2 and 14efcf865. What remains today is: an odds/schedule ingestion path, a 365-team registry (shared/ncaamTeams), and two orphan test files — one of which (kenpomCredentials.test.ts) would spawn a nonexistent script if KENPOM_EMAIL/KENPOM_PASSWORD were ever set in CI. No NCAAM model code is shipped.

[REFUTED] NFL has model code
  -> NFL has data ingestion and a rigorous nflverse/ESPN-sourced SQLite dataset build with multi-pass integrity gates, plus a UI presentation adapter — but zero projection or simulation code. The dataset pipeline itself is not committed to git yet.

[PARTIALLY_VERIFIED] Soccer has model code
  -> There is a real, shipped soccer model — analytical Dixon-Coles — but it is a Node .mjs, it is hardcoded to the 2026 World Cup (16 tier multipliers, two named fixtures already played), and it is not part of the Python engine. There is no general-purpose or club-league soccer model.

[VERIFIED] requirements.txt contents and what they imply
  -> Four packages, none of them machine-learning. numpy+scipy = RNG sampling and distribution math; pandas = tabular handling; requests = Action Network HTTP scraping. There is no sklearn/torch/xgboost anywhere in the sports engines — the only scikit-learn pin in the repo is in ml/dime-1.0/requirements.lock.txt (the dormant LLM post-training lane, alongside torch/peft/bitsandbytes/datasets). This is direct evidence that the "ML engine" is deterministic-formula + Monte Carlo statistics with offline-fitted constants baked into source (e.g. server/StrikeoutModel.py:12 `NegBin Dispersion (r = 22.20)`, :22 `OLS Calibration Layer kProj_cal = 1.0305 * kProj_raw + 0.3314`), not a learned model. Production never reads requirements.txt: Railway installs Debian apt packages (Dockerfile:23-28), so the pinned versions there are advisory for local dev only and can silently diverge from what actually runs.

CLUSTER: Stripe billing
====================================================================================================

[REFUTED] nine subscription states
  -> There is no nine-member enum or union anywhere in the repo. Three different, non-overlapping vocabularies exist: (a) the DB column `app_users.stripeSubscriptionStatus` is an unconstrained varchar(32) whose doc comment lists 8 raw Stripe statuses plus NULL — that is the closest thing to the claim, and only reaches 9 if you count NULL as a state, which the comment itself calls 'never observed'; (b) the app's own derived state machine `PlanStatusState` has exactly 4 members and is what the billing UI renders; (c) `SubscriptionKind` has 11 members but describes transitions written to the ledger, not states. The running code only makes decisions on 5 of the raw statuses (active, trialing → keep; past_due, unpaid, paused → revoke); incomplete/incomplete_expired/canceled reach only the persist-and-audit branch.

[PARTIALLY_VERIFIED] full webhook lifecycle
  -> 14 event types are genuinely handled in one switch in server/stripeWebhook.ts: checkout.session.{expired,completed}; customer.subscription.{created,updated,deleted,trial_will_end}; invoice.{upcoming,paid,payment_failed}; charge.{refunded,dispute.created,dispute.closed}; payment_intent.{succeeded,payment_failed}. That is a broad lifecycle — not 'full'. Not handled (they fall to the :1514 default no-op): customer.subscription.paused / .resumed, invoice.payment_action_required, invoice.finalized / .finalization_failed, charge.dispute.funds_withdrawn / .funds_reinstated, customer.deleted, payment_method.attached/detached, customer.subscription.pending_update_*. Materially: only the 8 access-changing types get the await-then-5xx treatment; the other 6 (checkout.session.expired, trial_will_end, invoice.upcoming, dispute.closed, payment_intent.succeeded, payment_intent.payment_failed) are acked 200 before processing, so a crash in those loses the event permanently with only a Discord alert.

[PARTIALLY_VERIFIED] atomic credit reservation/settlement
  -> There is no reservation/settlement pair. What exists is a single-phase post-hoc DEDUCTION in one route (POST /api/dime/wc2026, mounted at server/_core/index.ts:942). The deduction itself IS atomic and integer-only: a real db.transaction wrapping SELECT ... FOR UPDATE on the latest ledger row, an in-transaction balance check, and an append-only INSERT of int delta_credits/balance_after. But: (1) the pre-flight checkCredits at STEP 5 takes no lock and reserves nothing — it is advisory only; (2) the charge happens at STEP 13 only after the model has already answered and streamed, so on a lost race the user gets the answer free (`step.13.credit_RACE_BLOCKED`, creditsCharged=0), and a crash between response and deduct is also a free answer; (3) the request_id idempotency key is declared UNIQUE in the Drizzle schema but the schema file states production still carries it as a NON-unique KEY, so the double-charge guard is not actually enforced in prod; (4) nothing ever grants credits — every user silently defaults to a hardcoded balance of 100 (COALESCE ..., 100) and can only spend down. There is zero connection between Stripe and this credit ledger; the Stripe billing path (server/stripeWebhook.ts, server/stripe/*) contains no database transaction at all — entitlement grant, ledger writes, plan-quantity decrement and Discord role sync are separate un-transacted statements.

[REFUTED] Is there a public signup/checkout path, or is user creation manual/admin-only?
  -> A fully public, anonymous, pay-first signup path exists and is the primary one. Flow: anonymous visitor hits /checkout (public wouter route) → calls the unauthenticated tRPC `stripe.publicCreateEmbeddedCheckoutSession` → pays via on-domain Stripe Payment Element → `checkout.session.completed` webhook calls `createPendingUserFromCheckout`, which inserts an app_users row with pendingSetup=true, a random passwordHash and pendingStripeSessionId → /subscribe/success calls the unauthenticated `stripe.completeAccountSetup` (rate-limited, gated on `assertCheckoutSessionPaid` and a 72h claim TTL) to set email + password. What does NOT exist is a FREE signup: there is no `register` procedure, and account creation without payment is owner-only (`createUser: ownerProcedure`). So the revenue loop is not blocked on manual provisioning — but there is no free tier, no trial-without-card entry, and no way for a prospect to exist in the system before money moves.

  --- OPEN LOOPS ---
  * payment_events / subscription_events / entitlement_events — three append-only ledgers with zero readers
      breaks: Evaluation (and Adjustment/Memory): the Artifact is produced and persisted, but no process ever observes it
  * Stripe revenue events → product analytics
      breaks: Context/Memory: revenue never enters the metrics system, so no product decision can be conditioned on it
  * Webhook processing failure → Stripe redelivery is dead on arrival (claim-before-process)
      breaks: Adjustment: the retry the 5xx exists to trigger is neutralized by the idempotency claim
  * billingAlert() — every money-path failure terminates in a Discord message or a console line
      breaks: Artifact/Outcome: the alert creates no ticket, no row and no tracked state; if nobody reads the channel the event is gone
  * dime_credit_ledger has no grant/top-up writer and no link to Stripe
      breaks: Goal/Action: the credit system can only deplete; nothing replenishes it and no revenue event feeds it
  * charge.dispute.closed and checkout.session.expired are acked 200 before processing
      breaks: Outcome: a crash in these branches is unrecoverable — Stripe already got its 200, and the reconcile crons do not cover disputes or payment intents

  NOTES: Scope note: I excluded .claude/plugins-vendored/, .claude/skills/, node_modules/, dist/ and .git/ per instructions. The Stripe skills under .claude/skills/ and the `stripe:*` plugin skills are vendored third-party guidance and were never cited as evidence of anything Dime built. server/_core/aiCostMeter.ts is UNTRACKED (confirmed: `git ls-files server/_core/aiCostMeter.ts` returns nothing), so it is not on main and I did not use it as evidence for the credit claims.

Materially BETTER than the claims imply:
- Webhook idempotency is genuinely well-built. server/stripeWebhook.ts:117-148 uses insert-first-on-a-UNIQUE-index (not SELECT-then-INSERT) and correctly detects the drizzle-wrapped duplicate-key error via isDuplicateKeyError, with a comment explaining the exact bug that motivated it.
- Out-of-order protection exists: server/stripeWebhook.ts:155-160 `isStaleEvent` compares event.created against an app_users.lastStripeEventAt watermark.
- Money is integer cents everywhere it is persisted (drizzle/schema.ts:282, 442, 488, 490 are all `int(...)`); the only /100 is display formatting in a log line (server/stripe/paymentLedger.ts:110). One exception worth flagging: drizzle/dime.schema.ts:149-151 stores credit_before/credit_after/credit_delta as `decimal(10,2)` — but that is the dime_soak_test_results harness table, not the live ledger.
- Stripe API idempotency keys are used on outbound creates (server/routers/stripe.ts:77, 511, 614, 980; server/stripe/planProvisioning.ts:259, 264, 428, 532). Note the checkout keys are bucketed by `Math.floor(Date.now() / 60_000)` — a 60-second dedupe window, not a true per-intent key.

Materially WORSE:
- ZERO database transactions exist on the entire Stripe path. `grep '\.transaction(' server/ --include=*.ts` (non-test) returns only dime-wc2026.route.ts:160, dimeChatTrace.ts and routers/dimeChats.ts. Granting access, writing entitlement_events, writing payment_events, decrementing plan quantity (applyPurchaseToPlanQuantity) and syncing the Discord role are five independent un-atomic statements. Every ledger writer explicitly swallows its own errors by design ("bookkeeping must never break the money path", server/stripe/subscriptionLedger.ts:20-23), so a partial fulfillment is silent by construction.
- The claim-before-process ordering (openLoop #3) means the deliberate 5xx-to-invite-redelivery design at server/stripeWebhook.ts:1656-1658 does not actually work. This is the single highest-value defect I found in this cluster.
- The credit ledger's request_id uniqueness — the stated double-charge guard — is declared in Drizzle but explicitly NOT present in production (drizzle/dime.schema.ts:71-75 says so and names the workflow it was excluded from). Schema-as-documented and schema-as-deployed disagree on the one constraint that prevents double-charging.

Contradiction with existing project memory: the note "Stripe hardening handoff — CRITICAL reframed (no public signup exists)" is not accurate as of main today. A complete anonymous pay-first signup path is shipped and routed (client/src/App.tsx:286 → server/routers/stripe.ts:693 → server/stripeWebhook.ts:794 → server/routers/stripe.ts:1041). What does not exist is a FREE/unpaid signup.
