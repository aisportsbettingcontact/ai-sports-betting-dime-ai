## 2. The leakage-free claim — VERIFIED

**Verdict: the claim holds. Zero violations in 554,215 rows. The rule is also exactly tight.**

The 2025 shape-B rows carry no `season` or `week`; both were derived from a `dt` timestamp on
221 near-daily snapshots spanning 2025-08-03 → 2026-03-14. I did not trust the loader: I
rebuilt the game calendar independently from `SELECT season, season_type, week, playoff_round,
MIN/MAX(kickoff_utc) FROM game` and re-derived every row from its raw `dt`.

**Leakage.** For every one of the 462,425 labelled rows, `snapshot_ts` was compared against the
earliest kickoff of its assigned event.

462,425 + 91,790 = 554,215. The margins are real, not slack: the tightest cases (W13 Thanksgiving,
W17 Christmas) still clear the first kickoff by ~10h40m, and no row anywhere is on the wrong side.

**Tightness.** Leakage-freedom alone could be bought by labelling everything with a far-future
week. It was not: **0 rows** have any event opening after their snapshot but before their assigned
event. Every row carries the *immediate* next event. The rule is both safe and maximally
informative.

**Season assignment — correct, and not by luck.** Season boundaries are the midpoint of the
football-free gap, not the calendar year. close(2025) = 2026-02-08T23:30Z, open(2026) =
2026-09-10T00:20Z, so the 2025/2026 boundary falls in late May 2026. The latest snapshot
(2026-03-14) sits ~2.5 months inside season 2025 — comfortably clear, not a boundary coin-flip.
**194,879 rows carry a calendar-2026 timestamp**; a calendar-year rule would have misfiled every
one of them. The rule got this right. The 91,790 offseason rows correctly carry
`week`/`playoff_round` NULL, because season 2025 has no next event to forecast.

**No row loss.** Parsing `raw/depth_charts.csv` with a real CSV reader (not `wc -l`, which reports
1,114,906 because quoted fields contain newlines) yields exactly **1,106,729 rows = 552,514 shape A
+ 554,215 shape B**, matching the database row-for-row. My partition's 591,527 = 37,312 (2024
shape A) + 554,215 (2025 shape B). The decision to keep all 221 snapshots rather than
latest-per-week did keep everything: 554,215 loaded, 554,215 in the source.

**Position vocabulary — crosswalk correct, halves only partly queryable.** All 31 distinct shape-B
`pos_abb` values crosswalk, and every mapping is right: side markers collapse
(`LCB`/`RCB`/`NB`→`CB`, `LDE`/`RDE`→`DE`, `LDT`/`RDT`→`DT`, `LILB`/`RILB`→`ILB`,
`SLB`/`WLB`→`OLB`, `LG`/`RG`→`G`, `LT`/`RT`→`T`), `PK`→`K`, and `NT`/`MLB`/`FS`/`SS` stay
distinct. Measured column population in this partition:

|---|---:|---:|---|
| `depth_position`, `unit`, `franchise_id`, `bucket` | 100% / 98.7% | 100% | **yes** |

`depth_order` is the hazard: it is populated in both halves so it never nulls out, but the scales
are not the same quantity. In shape A it is the depth *team* (1st/2nd/3rd). In shape B it is
`pos_rank`, a rank within a position slot running to 15. `WHERE depth_order <= 2` means "starters
and backups" in 2024 and something materially different in 2025. This is documented in
`lib/depth_charts.py` and the schema comment; it is not a defect, but any cross-season query must
respect it.

**External validation: none, and none was attempted.** `depth_chart` has no historical public
source. ESPN publishes current depth charts only — proven, not assumed: the ESPN core API returns
the *identical* 92-athlete set for seasons 2023, 2024 and 2025 for the same team, and the site
roster endpoint returns an empty athlete list for a historical season
(`cache/f08/espn_roster_historical_probe.json`). No spot-check of the March 2026 snapshots against
ESPN's live data was performed, so **no ESPN validation of any depth-chart row is claimed.** All
591,527 rows are logged `NOT_COMPARABLE` with that reason. The 13 internal and derivation checks
run on every row — FK resolution, identity presence, week/round exclusivity, season_type
agreement, bucket vocabulary, crosswalk correctness, snapshot presence by shape, re-derived
season, re-derived bucket, re-derived event, leakage, tightness — **passed on all 591,527 rows,
with zero failures of any kind.**

### 3.4 `snap_count` — the split, stated honestly

**0 of 53,227 rows were validated externally. None. All snap_count validation below is INTERNAL.**

Pro-Football-Reference is the only authority that publishes snap counts and it is unreachable.
Four escalating attempts, all recorded in `cache/f08/pfr_block_evidence.json`: plain curl → 403;
curl with a complete Chrome header set → 403 whose body is a Cloudflare interstitial titled "Just a
moment…" (cached at `cache/f08/pfr_202409080buf.htm.http403`); the `widgets.sports-reference.com`
fallback → DNS failure; and a **real headless Chromium** driven through `agent-browser`, which
after 12s and 30s waits never left the challenge page and never rendered `#home_snap_counts`.
A genuine PFR sample was therefore **not achievable**, and I have not dressed internal checks up as
external ones.

What *was* done, on **all 53,227 rows**:

- **Byte-level fidelity against `raw/snap_counts.csv`**, the file this table was built from — all
  53,227 rows located in the source and all six snap/pct values reproduced exactly. **0 failures.**
- Structural: `gsis_id` and `game_id` FKs resolve; `franchise_id` is one of the two teams actually
  in that game; `season`/`season_type`/`week`/`playoff_round`/`pfr_game_id` agree with the parent
  game; `source_week`/`source_game_type` map correctly to the schema's REG/POST + round convention;
  every snap count is an integer in [0,200]; every pct in [0,1]. **0 failures.**

**Zero internal check failures across 53,227 rows.** This proves the loader is faithful and the
table is self-consistent. It does **not** prove the numbers are right — only PFR could, and PFR
is blocked.

One upstream observation, logged `NOT_COMPARABLE` against PFR rather than charged to the database
(5,967 rows: 4,351 ST, 1,394 defence, 222 offence): PFR's published percentages are stored to two
decimals and for 128 team-game units no single team denominator reproduces all of them. Example —
Buffalo's ST unit in `2024_01_ARI_BUF` fits D=27 for 25 of 31 players, but 17/27 = 0.6296 is stored
`0.63` (rounded) while 21/27 = 0.7778 is stored `0.77` (truncated). PFR's own rounding is
inconsistent. The stored values match the source file exactly, so this is an upstream artifact that
cannot be adjudicated while PFR is unreachable.

### 3.5 `roster_season` — 3,622 externally corroborated, 2,731 unobservable

ESPN **cannot** rule on historical roster membership, and I proved it rather than assuming it: the
core API returns byte-identical 92-athlete sets for seasons 2023, 2024 and 2025 for the same
franchise, and the site roster endpoint returns an empty athlete list for `season=2024`
(`cache/f08/espn_roster_historical_probe.json`). It serves the *current* roster whatever season you
ask for.

One genuine external signal remains: an athlete appearing in an ESPN box score for franchise F in
season S was demonstrably on F's roster that season. **3,622 of 6,353 rows (57%) are corroborated
that way** and logged `MATCH`. The remaining 2,731 are players who recorded no box-score
appearance for the franchise — membership is simply unobservable, logged `NOT_COMPARABLE`.
**0 internal check failures** (FKs, season_type/week exclusivity, `source_week` range,
`source_ordinal`).
