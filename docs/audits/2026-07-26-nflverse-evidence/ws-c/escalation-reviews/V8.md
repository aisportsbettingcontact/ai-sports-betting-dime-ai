# Escalation review — V8 8.2.0

**Escalations:** E1 (install-time RCE) **and** E7 (embeds a JavaScript engine; JS→R callback)
**Verdict:** **FINDING — High** (E1, install-time, exercised here)
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;**FINDING — Medium** (E7, `console.r` JS→R escape, on by default)
**Executes when:** E1 at `R CMD INSTALL`; E7 at call time, whenever JS is evaluated in a context
created by `V8::v8()`
**Ran on this machine:** E1 **YES** — a 47.5 MB static V8 engine was downloaded and linked

## Part 1 — E1: `configure` fetches and dot-sources a remote script

### Files read

`sources/V8/configure` (161 lines); fetched for reading only:
`https://autobrew.github.io/scripts/v8` — 36 lines, sha256
`4b09f45c605286d25d6ea8279664ece745f9883e34c4eb015e5b836e99307f39`, saved to
`scratchpad/task7-tmp/v8.sh`.

### What executes

**This branch is effectively unconditional on macOS arm64 — it is not a "no Homebrew" fallback.**
`configure:29-30` sets `HAVE_STATIC=1` on Darwin; `:44-50` then sets `DOWNLOAD_STATIC_LIBV8=1` for
`arm64`. That flag makes the test at `:85` (`command -v brew` **and** `-z "$DOWNLOAD_STATIC_LIBV8"`)
false *even though Homebrew is installed and was detected*, so the `else` fires. Homebrew was
present on this machine and V8 fetched anyway. Any darwin/arm64 source install takes this path:

```
configure:91     curl -sfL "https://autobrew.github.io/scripts/$PKG_BREW_NAME" > autobrew
configure:92     . ./autobrew
```

Again: unpinned URL, no checksum, dot-sourced. The Linux sibling at `configure:95-96` pins a
version tag (`.../12.4.254.21/get-v8-linux.sh`) — the macOS path does not.

The fetched script selects a bottle by platform (`v8.sh:1-11`), prints it (`:14`), and:
- `:20-25` — `curl -sSL $bottle -o libs.tar.xz`; `tar -xf ... -C $PWD/.deps`; `rm`
- `:28-31` — renames `libv8_monolith.a`, hardcodes `PKG_LIBS`/`PKG_CFLAGS` with
  `-DV8_COMPRESS_POINTERS -DV8_ENABLE_SANDBOX`
- `:34` — **writes `src/Makevars` itself** and `:36` **`exit 0`** — the dot-sourced script
  terminates configure, so `configure:99-160` (the compiler feature tests, the libv8 presence test,
  the ANTICONF error handler) never run. A remote script decides the entire build.
- `:17` — honours `DISABLE_AUTOBREW`

### Verdict (E1)

**FINDING — High.** The largest single unverified binary in the closure: ~47 MB of a JIT-compiling
JavaScript engine, fetched from a GitHub release with no checksum, chosen by a script fetched from
a mutable URL, which also seized control of the build by writing `Makevars` and exiting. A JIT is
the worst possible thing to accept unverified — it allocates W^X memory and emits native code by
design, so a tampered blob has an unusually clean path to persistent native execution. No evidence
of tampering was found; the bottle tag `v8-14.6.202.26` is a normal autobrew release. But the
enduring statement is not "code ran during install" — it is that **~47 MB of third-party binary of
unverified provenance is resident in the installed library and `dyn.load`s into any R session that
touches `gt`, `juicyjuice`, `reactable` or `reactR`**. `cleanup:2-3`
(`rm -f … autobrew get-v8*.sh` then `rm -Rf .deps`) destroyed both the fetched script and the
extracted archive, so `V8.so` is the only remaining witness. WS-B's PASS on `V8_8.2.0.tar.gz` does
not cover this — see `STRUCTURAL-LIMITATIONS.md` §L4.

## Part 2 — E7: `console.r` gives JavaScript a route back into R

### Files read

`sources/V8/R/callback.R` (52 lines, in full), `sources/V8/R/V8.R:136-230`,
`sources/V8/src/bindings.cpp:285-350, 508-551`.

### What executes

`R/callback.R` defines four R functions reachable **from inside the JS VM**:

| JS API | R function | What it does |
|---|---|---|
| `console.r.call(fn, args)` | `r_call` (`callback.R:4-13`) | `FUN <- eval(parse(text=strfun))` then `do.call(FUN, ARGS)` |
| `console.r.get(expr)` | `r_get` (`:16-22`) | `x <- eval(parse(text = str))` |
| `console.r.eval(code)` | `r_eval` (`:25-33`) | `source(textConnection(str))` — **arbitrary R, evaluated in the global environment by default** |
| `console.r.assign(n, v)` | `r_assign` (`:36-44`) | `assign(name, VAL, globalenv())` — writes the global env |

Wiring: `bindings.cpp:325-342` register `console_r_call`/`_get`/`_eval`/`_assign`; each calls
`r_callback(...)` at `:291-311`, which resolves the name in `Rcpp::Environment::namespace_env("V8")`
and invokes it. `console_template()` (`bindings.cpp:514-522`) attaches them under `console.r`.

**Gating:** `make_context(bool set_console)` installs the console object only
`if(set_console)` (`bindings.cpp:541-548`). The R default is
`v8 <- function(global = "global", console = TRUE, ...)` (`R/V8.R:136`) — so **`console.r` is
present in every context created by a default `V8::v8()` call**.

`ctx$source(file)` (`R/V8.R:175-182`) accepts a URL: `grepl("^https?://", file)` → `curl(file)` →
`evaluate_js(readLines(...))`. The package's own examples do exactly that
(`R/V8.R:108` `cdnjs.cloudflare.com`, `:122` a plaintext `http://coffeescript.org` URL).

**Every `ctx$source()` in this closure reads a bundled path, not a URL** — verified:
- `juicyjuice/R/css_inline.R:19-22` — `system.file("dist/bundle.js", package="juicyjuice")`
- `reactR/R/babel.R:20-25` — `system.file("www/babel/babel.min.js", package="reactR")`
- `reactable/R/reactable.R:850` — `system.file("htmlwidgets/reactable.server.js", package="reactable", mustWork=TRUE)`

### Verdict (E7)

**FINDING — Medium.** The JS↔R boundary is not a sandbox by default: any JavaScript that runs in a
default `v8()` context can call `console.r.eval("<any R code>")` and execute R at global scope.
That is a deliberate, documented feature, and it is fine when the JS is a trusted bundled asset —
which is the case for all three consumers in this closure. It becomes a real vulnerability the
moment anyone points `ctx$source()` at a URL (which the package's own documentation demonstrates
twice, once over plaintext HTTP), or evaluates JS derived from untrusted input, because the JS
engine then has a full escape hatch instead of being a containment boundary. The medium rating
reflects that no code path in this closure currently feeds untrusted JS to a V8 context — only that
the guard rail is off by default if anyone ever does.

## Defender action

**E1:** install binaries; or for source builds set `DISABLE_AUTOBREW=1` (`v8.sh:17`) and supply
libv8 via `V8_PKG_CFLAGS`/`V8_PKG_LIBS` (`configure:19-23`) or Homebrew `v8`; verify the resulting
`V8.so` is small (dynamically linked) rather than ~47 MB; egress-restrict the build host. Track V8
CVEs against `14.6.202.26` — a static engine gets no OS patching.

**E7:** any code that evaluates JavaScript not shipped inside the calling package must use
`V8::v8(console = FALSE)`, which skips `console_template()` entirely (`bindings.cpp:541`). Never
call `ctx$source()` with an `http://` or `https://` argument; vendor the JS and load it via
`system.file()`, exactly as juicyjuice, reactR and reactable already do. If V8 is not needed at all,
note that it enters this closure only through `gt` → `juicyjuice` (HTML email/table inlining) and
`reactable` — neither is required for the core nflverse data path.
